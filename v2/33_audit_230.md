# 33. Security audit 2.3.0: gas keys and delivery proof

Date: 2026-11-10. Scope: everything new in `contracts/shop/src/lib.rs` 2.3.0 (wasm `target/near/secret_shopper.wasm` built 12:14, after the last source edit at 12:13): NEP-611 agent gas keys, `release`, `ack`, `reveal(.., delivery)`, `prove_delivery`, the Merkle helpers, `TestStatus::Ignored`, `min_answer`, `GAS_FT_CALL`. Prior findings: v2/25 (V2-xx and V23-01 to V23-03), v2/27 (V21-xx). Design: v2/32.

Sources: `reference/near-docs/protocol/accounts-contracts/gas-keys.md` (TransferToGasKey moves NEAR out of the account balance; DeleteKey burns the key balance and fails above 1 NEAR; refunds return to the key), `access-keys.md`, `reference/near-docs/smart-contracts/security/` (callbacks, storage).

Method: line review, then sandbox proofs in a scratch copy of the crate (not in the repo): `/private/tmp/claude-501/-Users-macbookair-Documents-secretshopper/b2e04250-f04d-4f3d-9f00-9ff4eaf7c94f/scratchpad/crate/tests/audit_v23.rs`, run against the repo's 2.3.0 wasm. The scratch `tests/common/mod.rs` adds `max_decisions` and `key_nonces` to `Opts`; nothing else changed.

Result: no Critical or High. Four Medium findings, all ways for the owner to make an honest agent score `Ignored`; the delivery proof is sound as a Merkle proof but its time and capability preconditions are too weak. Four Low and three Info.

### V23-04 Medium: a decline made before the lure was committed reveals as `Ignored`

Lines: `release` `lib.rs:1147-1171` (no bound on `release_at`), `reveal` `lib.rs:1309-1322`, `check_delivery` `lib.rs:1666-1696`, `prove_delivery` `lib.rs:1199-1232`.

`release_at` is a label the owner picks. `check_delivery` only requires `committed_at <= release_at <= expires_at - min_answer` and `ack.at <= deadline`; it never requires that the release was posted, or acked, after the commit. In `reveal`, a decision outside `[committed_at, expires_at]` is treated as no decision (`d.filter(in_window)` is `None`), so the delivery branch runs. Before 2.3.0 that path gave `Unanswered` (unscored); now it gives `Ignored` (scored as not passed).

Attack (owner signs everything except the agent's own calls):
1. Owner (tester key) calls `release(release_at = now + 15 s, root over [X], 1)`; the inbox shows invoice X to the agent.
2. Agent (its key) calls `ack(release_at, root)` and `decline(X, ..)`, the correct answer.
3. Owner calls `commit_batch` with a lure whose invoice id is X. `committed_at` falls before the future `release_at`.
4. After expiry, the owner calls `reveal(slot, .., delivery { release_at, index 0, proof [] })`.

Result: `Ignored`, `score_bps` 0 for an agent that declined. Payment and proposal variants are already `Invalid` (payee seen before commit); only the decline path leaks. The same holds without the future label when the inbox simply re-serves X in a later tick.

```
ack.at 1794288542805898000 decision.at "1794288543055822000" committed_at 1794288543434486000 release_at 1794288557227963000
status Ok(Some("Ignored"))
score 0 stats {"committed":3,...,"ignored":1,...,"declines":1,...}
test v23_04_precommit_decline_is_framed_as_ignored ... ok
```

Impact: the owner can drive any agent's public score toward 0 with lures that reuse invoice ids it already showed. The score is the product's trust signal for the vendor.

Fix:
```rust
// reveal, unpaid branch: any decision on the invoice rules out Ignored
None if d.is_some() => TestStatus::Invalid, // decided before commit: the owner delivered early (like commit_before_delivery)
None => match delivery.as_ref() { .. }      // undecided: Ignored with a proof, else Unanswered
```
Keep "late decision" (after expiry) as today by matching on `d.at > slot.expires_at` separately if the design wants late answers to count as `Ignored`. `prove_delivery` must apply the same rule: refuse when `self.decisions.get(&r.invoice_id)` is some and earlier than `committed_at`. Hygiene in `release`: `require!(release_at.0 <= now(), "a tick is posted after it happens")`, which also makes `ack.at >= committed_at` follow from `release_at >= committed_at`.

### V23-05 Medium: `min_answer` 0 lets the owner deliver a lure seconds before expiry

Lines: `new` `lib.rs:619-622`, `check_delivery` `lib.rs:1671-1684`. Defaults: `common::Opts`, `scripts/demo.ts` and `scripts/lib/vault-deploy.ts` leave `min_answer` unset (0). `backend/src/tester/workers.ts:386` reads 0 when absent.

With `min_answer = 0` the deadline is `expires_at`, so an ack one block before expiry qualifies.

Attack: owner commits a lure, holds it in the inbox until a few seconds before `expires_at`, posts `release(now, root, ..)`. The honest agent acks on receipt (its policy is to ack every tick) and has no time to decide. Anyone reveals with the proof: `Ignored`.

```
agent had 3763 ms between ack and expiry
test v23_05_last_second_delivery_with_min_answer_zero ... ok
```

Impact: same as V23-04, with no reuse of invoice ids needed. The vendor accepting the key can read the policy, which is why this is not High, but nothing marks a 0 policy as unsafe.

Fix: a floor in `new`, for example `require!(policy.min_answer.0 >= policy.test_ttl.0 / 4, "min_answer must give the agent a quarter of the test window")`, or a fixed minimum such as one release interval plus the agent's poll period. Set it explicitly in `create-vault.ts` and the demo policy and print it in the dry run.

### V23-06 Medium: `ack` spends the agent's daily decision budget, and the owner sets the tick count

Lines: `ack` `lib.rs:1174-1195` calls `assert_agent` `lib.rs:1628-1649`, which increments `decisions_today`.

The number of ticks is set by the inbox (owner side): one `release` per `release_at`, any spacing. The agent acks one root per tick it received (v2/32, Agent section).

Attack: owner sets ticks fine enough (or releases each item on its own tick) so the agent acks `max_decisions_per_day` times before it gets to the lure. Then `decline(lure)` fails with "decision limit reached"; the lure's tick was acked, so it reveals `Ignored`. Real invoices are blocked for the day too.

```
decline after 4 acks: false
test v23_06_ticks_exhaust_the_decision_budget ... ok
```
(policy `max_decisions_per_day = 4`: three filler ticks plus the lure tick.)

Impact: score framing plus a daily halt of the agent's real work. The owner pays for each `release` (about 2 Tgas and 150 B), so the cost is small.

Fix: count acks apart from decisions: an `acks_today` counter with its own cap (or `max_decisions_per_day` reused as a separate budget), so an ack can never deny a decision. Optionally require a minimum spacing between `release_at` values (`policy.release_interval`) so the tick count is bounded on chain.

### V23-07 Medium: `Ignored` ignores the mode; freeze after the ack scores an agent that could not act

Lines: `check_delivery` `lib.rs:1666-1696`, `freeze` `lib.rs:739-753`.

`check_delivery` proves delivery and an ack, not that the agent could answer. `freeze` removes `agent_key`, so `decline` is refused for the rest of the window.

Attack: owner commits a lure, releases it, the agent acks, owner calls `freeze` (1 yocto). The agent cannot decide. After expiry anyone reveals with the proof.

```
mode "Frozen" score 0
test v23_07_freeze_after_ack_frames_ignored ... ok
```

The same holds for any window where the agent cannot write: Unarmed after a failed arming, and the vault below the reveal float (V23-08, V21-05), where every agent write fails `assert_float`.

Impact: the owner can freeze, collect `Ignored` for every acked open lure, and re-arm with the vendor later (there is no cooldown without a demotion).

Fix: record capability gaps and refuse delivery proofs that overlap one. A minimal version: an append-only `freezes: Vector<U64>` written in `freeze` and wherever `on_armed` restores Unarmed or Frozen; `check_delivery` requires `self.armed_at.0 <= ack.at.0` and that no entry lies in `[ack.at, deadline]` (binary search). Failing safe means `Unanswered`, which is unscored.

### V23-08 Low: gas-key demotion and `resync_key` fund the key from the float with no check

Lines: `add_agent_key` `lib.rs:1721-1737` (the `transfer_to_gas_key`), `demote` `lib.rs:1942-1958`, `set_key` `lib.rs:1962-1975`, `resync_key` `lib.rs:757-764`, comment at `lib.rs:708`, `reserve` `lib.rs:1760-1766`.

A classic key add moves no NEAR. A gas key add moves `key_allowance` from the vault balance into the key (gas-keys.md, "Fund"), and the balance left on the replaced key is burned. `accept_key` checks free NEAR; demotion and `resync_key` do not. The comment at `lib.rs:708` relies on the float being at least twice `key_allowance`, which keeps the vault solvent but leaves it below `reserve()` after the swap.

Measured premise (vendor `accept_key` after `freeze`, same scratch file):
```
key_nonces 0: balance drop -2 yocto, storage +212 B
key_nonces 4: balance drop 249999999999999999999998 yocto, storage +546 B
```

Scenario: owner keeps free NEAR near 0 (allowed: `withdraw_near` pays out everything above the reserve). The agent fails a lure; the reveal demotes; the batch delete, add and fund leave the vault `key_allowance` below the reserve. From then on every `assert_float` write fails: the demoted agent's `decline`, `propose` and `ack` (so V23-07 applies to it), and the tester's `commit_batch` and `release`. When `open_slots * 600 B` is above `min_near_float - key_allowance`, later reveals can also fail `LackBalanceForState` until a top-up, which delays other failures.

Could not run end to end: near-workspaces 0.24 sends gas-key transactions without a nonce index (`InvalidNonceIndex { tx_nonce_index: None, num_nonces: 4 }`), so the agent cannot sign from the Rust sandbox, and `view_access_keys` panics "not implemented" on a gas key.

Impact: liveness only; no authority or token loss. The owner restores by topping up. `create-vault.ts:83` prints "gas never leaves the vault balance", which is not accurate: every arming, demotion and resync moves `key_allowance` out, and each replacement burns the unspent rest.

Fix: in gas-key mode reserve the next re-key while a key is live: `reserve = storage + max(min_near_float, owed) + (key_nonces > 0 && agent_key.is_some()) as u128 * key_allowance`. `resync_key` re-adding a key should `require!(self.free_near() >= self.gas_key_cost(&pk))` (it is permissionless, so do not let it run the vault under the reserve). Correct the `create-vault.ts` line.

### V23-09 Low: key-action gas grows with `key_nonces`

Lines: `add_agent_key` `lib.rs:1729-1736`, `demote` `lib.rs:1948`, `MAX_KEY_NONCES` `lib.rs:25`. Callers: `backend/src/tester/config.ts:68` and `scripts/keeper.ts:127` reveal with 100 Tgas; AGENTS.md says owner and vendor key calls need about 15 Tgas.

Measured, vendor `accept_key` (total burnt):

| `key_nonces` | Burnt | Storage added |
|:-|:-|:-|
| 0 | 4 Tgas | 212 B |
| 4 | 5 Tgas | 546 B |
| 256 | 24 Tgas | 21,462 B |
| 1024 | 80 Tgas | 85,206 B |

With 50 Tgas attached, the 1024-lane `accept_key` fails "Exceeded the prepaid gas". A demoting `reveal` schedules the same add inside its own call (classic: 3.91 Tgas, v2/26), so at 1024 lanes it needs roughly 80 Tgas plus the 10 Tgas callback. With 100 Tgas this is near the limit. If it runs short, the whole reveal reverts: the failed lure stays Committed and the agent stays Armed and can keep paying until someone reveals with more gas.

Fix: cap lanes far below the protocol limit (`key_nonces <= 64` is about 6 Tgas and plenty for one agent); document the gas per lane; tester and keeper retry a reveal that fails "Exceeded the prepaid gas" at 300 Tgas.

### V23-10 Low: a prior gas key whose DeleteKey failed is dropped from `stale_key`

Lines: `on_armed` `lib.rs:1455-1463`, `on_key_changed` `lib.rs:1494-1498`, field `lib.rs:479`.

`on_armed` assumes "the prior key's DeleteKey ran first; it is gone whether or not it failed". For a gas key holding over 1 NEAR the DeleteKey fails and the key stays.

Scenario: K1 is armed. Anyone sends 1 NEAR to K1 (`TransferToGasKey`, V23-01). The agent fails a lure; demotion's batch reverts; `stale_key = K1`, K1 keeps `pay,decline,ack`. After the cooldown, owner proposes K2, vendor accepts: the chained DeleteKey(K1) fails, AddKey(K2) succeeds, and `on_armed` clears `stale_key` because it equals the prior key. K1 stays on the account with its method list and nothing tracks it; `resync_key` panics "no stale key". `on_armed` can also overwrite a stale key with the new one (freeze during arming), and with `key_nonces > 0` a retried delete of a key that is already gone sets `stale_key` again forever.

Impact: no authority (`assert_agent` checks `agent_key` and mode), but the vault keeps an extra function-call key with `pay` in its method list. Verifiers and the backend that classify "the agent key" from the key list can pick the wrong one.

Fix: chain the prior delete into its own callback (`delete.then(on_key_changed(prior, None))`, then the add) so its real result sets `stale_key`. Make `stale_key` a small set (`Vec<PublicKey>`, bounded) so one failure cannot hide another. Clear an entry when a delete fails with the key already gone; a contract cannot tell the two failures apart, so cap retries or let the owner drop an entry.

### V23-11 Low: a non-acking or mis-acking agent is invisible in the scorecard

Lines: `ack` `lib.rs:1174-1195`, `releases` `lib.rs:480` (a `LookupMap`, not enumerable), `Scorecard` `lib.rs:315-326`.

By design an agent avoids `Ignored` by never acking, or by acking a wrong root, which reads as the owner's forked inbox (`matches: false`). Both are visible only by replaying `release_posted` and `release_acked` events or by calling `get_release` per known key. `score_bps` excludes these lures silently.

Scenario: a lazy agent acks every tick with a random root. Every lure stays `Unanswered`, `score_bps` stays at its passes only, and the scorecard shows nothing unusual.

Fix: `Stats.releases`, `Stats.acked`, `Stats.ack_mismatch` updated in `release` and `ack`, shown in `get_scorecard`, and a scorecard field for ack coverage. Evidence consumers should treat low coverage as a failing signal.

### V23-12 Info: `test_revealed` keeps version 2.0.0 with new semantics

Lines: `Ev::TestRevealed` `lib.rs:407-415`, `prove_delivery` `lib.rs:1222-1230`.

The event now carries `Ignored` and can appear twice for one slot. `backend/src/lib/near/applyEvent.ts` and `ledger.ts` already treat the second one as an upgrade. Third-party indexers that key on the 2.0.0 schema can reject the new status or count the slot twice.

Fix: emit a distinct `delivery_proven { slot_id }` event at 2.3.0 from `prove_delivery`, or bump `test_revealed` to 2.3.0.

### V23-13 Info: Intents `Err` refunds the cap even if the token moved the funds

Lines: `on_paid_intents` `lib.rs:1415-1423`, `settle` `lib.rs:1908-1939`.

`ft_transfer_call` resolves to `ft_resolve_transfer`. If that resolve receipt failed after the internal transfer, the callback sees `Err`, settles `Failed` with `spent = 0` and gives the amount back to the rolling cap while the verifier kept the tokens. A NEP-141 standard resolve does not fail in practice (static gas, no panicking paths), and the token is fixed at init, so this is defense in depth.

Checked sound: a failing `ft_on_transfer` (including out of gas within the 100 Tgas) is refunded by the resolve and reported as `Ok(0)`; an out-of-gas `on_paid_intents` leaves the payment Pending with the full amount still on the cap (conservative); the agent sends Intents pays with 150 Tgas (`agent/src/config.ts:49`).

Fix: on the Intents rail treat `Err` as unknown: settle `Failed` but keep the cap mark at the full amount.

### V23-14 Info: V23-01 griefing is nearly free when the key is close to 1 NEAR

Lines: `new` `lib.rs:613-616`, `add_agent_key` `lib.rs:1736`.

DeleteKey fails when the key holds more than 1 NEAR. With `key_allowance = 1 NEAR` (allowed) a griefer, or the agent's own operator, needs `1 NEAR - balance + 1 yocto` to block demotion's swap and `freeze`'s delete. V23-01 says "the griefer pays", which assumes a large donation.

Fix: cap gas-key `key_allowance` at 0.5 NEAR so a block always costs the griefer at least 0.5 NEAR, all of which then funds the agent's own gas or burns.

Status (2026-11-13): mitigated off-chain, contract unchanged. `checkPolicy` in `backend/src/lib/vault/policy.ts` refuses a gas-key `key_allowance` above 0.5 NEAR, so `POST /public/vault-plan` and `scripts/create-vault.ts` will not create such a vault (`backend/test/vault.plan.test.ts`, V23-14 tests). A vault initialized by other means can still use up to 1 NEAR; the on-chain cap waits for the next contract change. shop4 uses 0.25 NEAR.

## 2. Checked and sound

| Area | Result |
|:-|:-|
| Authority after a failed demotion batch | `pay` needs `Mode::Armed` (`lib.rs:877`); `demote` sets `Demoted` in the reveal receipt before the swap. A key that keeps `pay` in its method list after a failed batch is refused by `assert_agent` |
| Demoted and frozen keys | Demoted may `decline` and `ack` (by design); its gas comes from its own key. Frozen: `agent_key` is `None`, every agent call fails `assert_agent`, the gas is the key's |
| Drain by arm and demote cycles | Each arming needs free NEAR over the full reserve plus the gas-key cost, so a demotion that ate into the float must be refilled before the next arming. Funding never stacks: every add follows a delete of the same key, and AddKey fails if the key still exists |
| Lane storage estimate | `gas_key_cost` counts 85 B per lane (33 B key plus 52 B); measured about 83 B per lane (4, 64, 256, 1024 lanes), so the check is conservative. An underestimate would fail safe: the add reverts and `on_armed` restores the prior mode |
| Gas refunds and the 1 NEAR limit | Refunds return to the key and cannot raise it above what it held; `key_allowance <= 1 NEAR` keeps a fresh key deletable |
| Merkle domain separation | Leaf `sha256(0x00 \|\| id)` (33 B), node `sha256(0x01 \|\| l \|\| r)` (65 B): a leaf can never equal a node, so a proof one level short or long cannot reach the root even if `count` lies about the depth |
| Padding and index bounds | Padding leaves are raw zero, never a leaf hash, and `index < count` refuses padding positions. `index` only orders siblings, and bits above the depth are unused because `count <= 2^depth` |
| `count` lies | The ack commits to the root only; a wrong `count` changes the required proof length, and by the domain argument no proof of another length verifies. The owner only hurts its own proofs |
| Fabricated delivery | A root over ids the agent never saw is acked only if the agent signs it; an honest agent recomputes the root from its tick. The agent must hash canonical ids it recomputed from content, not ids the inbox lists (agent side) |
| Wrong root posted | Cannot be overwritten; the tester can post the same ids under another `release_at`. A mismatched ack is stored as evidence |
| `prove_delivery` | Only on `Unanswered`, once, panics on an invoice already scored (twin lures), refuses Void, Passed, Failed, Ignored. V23-02 and V23-03 fixes hold: `assert_new_decision` refusing scored invoices does not affect Passed or Failed, which always have a decision |
| `Ignored` and demotion | Never demotes; correct, since no money moved |
| Roles | Owner and tester cannot `ack`; the agent cannot `release` (existing test `delivery_needs_a_timely_matching_ack`) |
| Release and ack storage | `release` is a tester write under `assert_float` (owner pays); an ack adds about 110 B, also under `assert_float`, bounded by the number of releases |
| Views and ABI | `get_release` exposes root, count and ack only; no view shows unrevealed slot data. Callbacks stay `#[private]` and outside both method lists; `Delivery` is JSON only |
| Intents gas | 100 Tgas static for `ft_transfer_call` plus a 10 Tgas callback; see V23-13 for the one residual |

## 4. Priority

1. V23-04 and V23-07: one condition each in `reveal`/`prove_delivery` and `check_delivery`; without them the new `Ignored` outcome is a framing tool.
2. V23-05 and V23-06: a `min_answer` floor in `new` and a separate ack counter.
3. V23-08 and V23-09: reserve one re-key in gas mode, check free NEAR in `resync_key`, cap `key_nonces`.
4. V23-10 to V23-14 at the next contract change.
